# قدم ۴ — بعدش چیکار کنیم؟ (نقشه‌ی راه)

تا این‌جا یه بک‌اند واقعی و زنده دارین که:
- کاربر واقعی با یوزر/پسورد لاگین می‌کنه (نه اون پسکد ساده‌ی قبلی)
- ستون‌های راستر، اعضای تیم، و تعطیلات رو از یه دیتابیس واقعی PostgreSQL می‌خونه/می‌نویسه
- آماده‌ست که چند نفر هم‌زمان باهاش کار کنن (چون دیگه localStorage مرورگر نیست)

## چیزی که هنوز مونده

**۱) وصل کردن `Shift_Roster.html` به این API**
الان اون فایل داده‌هاش رو از `localStorage` می‌خونه (`loadRoster()` / `saveRoster()`). باید این دو تابع عوض بشن که به‌جای مرورگر، از همین API که ساختیم بخونن/بنویسن. این یعنی:
- بعد از لاگین موفق، `token` رو نگه داریم (مثل همون صفحه‌ی تست `/admin`)
- `loadRoster()` بشه یه `fetch('/api/roster/entries?from=...&to=...')`
- هر تغییر تو یه خونه (اضافه/حذف اسم) بشه یه `fetch('/api/roster/entries', {method:'PUT', ...})`

این یه تغییر مشخص و قابل‌انجامه — وقتی آماده بودین بگین **"بریم سراغ وصل کردن Shift_Roster"** تا دقیقاً همون تابع‌ها رو باهم بازنویسی کنیم.

**۲) همین کار برای گزارش‌های SDCM / AICC / SLA**
اون سه‌تا گزارش فعلاً کاملاً client-side و مبتنی بر آپلود فایل اکسل هستن — نیازی به دیتابیس ندارن مگر بخواین تاریخچه‌ی گزارش‌ها رو هم ذخیره کنین. این می‌تونه یه فاز جدا باشه.

**۳) پنل مدیریت کاربران**
الان فقط با اسکریپت (`create_admin.js`) می‌شه کاربر ساخت. یه صفحه‌ی واقعی برای لیدرشیپ/ادمین که بتونن کاربر اضافه/غیرفعال کنن یا نقششون رو عوض کنن.

**۴) وقتی آماده‌ی روی سرور واقعی (نه VM شخصی) بودین**
اون‌موقع باید:
- `systemd` سرویس بسازیم که بک‌اند خودش بعد از ریبوت سرور بالا بیاد
- `nginx` جلوش بذاریم (reverse proxy + گواهی SSL رایگان با Let's Encrypt)
- `NODE_ENV=production` و یه `JWT_SECRET` واقعی و امن

این بخش رو فعلاً کنار می‌ذاریم چون گفتین اول می‌خواین رو VM شخصی خودتون و به‌صورت localhost ببینینش.
